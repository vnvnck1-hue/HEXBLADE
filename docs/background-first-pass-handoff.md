# 배경 1차 제작 인수인계 — 큰 파츠 4종

작성: 2026-10-03 · 대상: Claude / Codex 공통

문서 정리: 2026-10-04. 아래는 첫 제작의 공통 기준이며, 별도 작업에서 이미 생성된 파일이 있더라도 이번 문서 요청이 추가 제작이나 덮어쓰기를 승인하지는 않는다.

**이번 요청의 범위: 계획·인수인계 문서 작성만. 이 요청을 근거로 모델링·텍스처 제작·게임 적용을 시작하지 않는다.**

사용자의 마지막 지시는 “이 문서를 기반으로 첫 작업에 착수할 것이지만, 아직 하지는 말 것”이다. 이 문서를 읽었다는 이유로 제작을 시작하지 말고, 사용자가 해당 작업자에게 명시적으로 착수를 요청한 뒤 아래 순서를 실행한다. 지금은 에셋 생성, 엔진 실행, 다른 에이전트에게 작업 지시, 커밋·푸시를 하지 않는다.

## 빠른 인수인계

- **먼저 만들 것:** F01 바닥 → W01 벽 → A01 작업대 → A02 수납장, 큰 파츠 4종만.
- **먼저 적용할 곳:** 본편을 바꾸지 않는 8×8m 시험 공간. 바닥 16장, ㄱ자 벽, 작업대·수납장 각 1개.
- **맞춰야 할 인상:** 최신 v6의 저채도 보라 바탕과 제한적인 코랄 포인트. 넓은 칠한 명암과 두툼한 베벨, 조용한 전투 바닥.
- **완성의 판단:** 실제 게임 카메라에서 플레이어·적·공격 표시가 잘 읽히고, 반복 이음과 충돌이 정상이어야 한다.
- **아직 하지 않을 것:** 감염 레이어, 작은 장식, 본편 배경 일괄 교체. 제작 착수는 별도 사용자 지시를 기다린다.
- **다른 작업자와의 경계:** 시작 전에 최신 작업 기록과 파일을 확인한다. 기존 파일이나 별도 제작 결과가 있어도 이 문서만으로 덮어쓰기 권한이 생기지 않는다.

## 1. 이번 작업의 목적

승인된 보라·코랄 핸드페인팅 배경을 **실제 Godot 카메라와 플레이어가 있는 작은 검증 공간**에 처음 구현한다. 작은 장식 없이도 큰 면의 색감·칠한 부피감·공간의 성격이 살아나는지를 먼저 판단한다.

- 세계의 기본 재질은 기존 1번 컨셉, 감염은 기존 3번 컨셉을 독립 레이어로 덧씌우는 방향이다.
- 첫 제작에는 기본 상태만 만든다. 감염 파츠는 이번 4종에 포함하지 않는다.
- 우주 청소업체의 정비시설을 연상시키는 실용적인 산업 공간. 이번 작업이 내러티브 대안 전체의 채택이나 스토리 변경을 의미하지 않는다.
- 사용자는 저채도·낮은 명도, 약간 카툰식인 핸드페인팅을 요청했다. 이후 TFT 배경 레퍼런스로 정리된 **최신 v6 색감**을 기준으로 한다.
- Blizzard식으로 요청한 두툼한 형태·칠한 명암과 TFT 레퍼런스의 보라/코랄 색상 관계를 적용한다. 특정 작가의 화풍을 그대로 복제하는 목표가 아니라, 큰 색면·부드러운 명암·선택적인 모서리 강조라는 제작 요소로 옮긴다.
- 성공 기준은 “Blender에서 멋진 단품”만이 아니라 **현재 게임 화면에서 플레이어·적·공격 표시가 잘 읽히는 배경**이다.

## 2. 승인된 범위와 우선순위

| 순서 | ID / 파츠 | Godot 기준 X × Y × Z (m) | 첫 제작에서 확인할 것 |
|---|---|---|---|
| 1 | F01 기본 바닥 | 2 × 0.2 × 2 | 넓은 보라색 면, 반복 이음, 전투 표시 가독성 |
| 2 | W01 벽 패널 | 2 × 3 × 0.25 | 바닥과 명도 분리, 큰 면의 부피감, 베벨 표현 |
| 3 | A01 작업대 | 2 × 1 × 0.75 | 큰 코랄 상판과 보라 하부, 정비시설의 성격 |
| 4 | A02 수납장 | 1 × 2 × 0.5 | 높이가 있는 큰 덩어리, 벽과 프랍의 구분 |

첫 공간은 **8×8m 바닥 + ㄱ자 벽 + 작업대 하나 + 수납장 하나**다. F01 16장으로 바닥을 채운다. 전체 키트의 `assembly_instances.json`에 있는 30장 혼합 바닥 예시는 이번 범위가 아니다.

이번에 제외할 것:

- F02~F05 대체 바닥, 안전선/데칼, 벽 이음 덮개/코너 장식/몰딩, 문과 개폐 기구.
- 배관, 난간, 공구판, 램프, 공구, 컵, 천, 빗자루 등 작은 소품.
- 감염 줄기·막·포낭 및 감염도 시스템.
- 신규 상호작용, 수납장/서랍 개폐, 파괴, 전투 규칙·캐릭터 수정.
- 모든 전투방/보스방의 일괄 교체, 전역 팔레트·조명·후처리의 일괄 변경.

**범위 우선순위:** 이 문서가 첫 제작 범위와 순서를 정한다. 전체 키트 `DESIGN.txt` 11절의 문틀부터 만드는 일반 순서는 이번 첫 제작에는 적용하지 않는다. 전체 키트의 치수·피벗·재질 계약은 계속 유효하다.

벽의 회보라색 밝은 면은 W01 시트를 기준으로 한다. 위 HEX는 팔레트 기준점이지, 조명까지 포함한 최종 화면 RGB를 강제로 일치시키라는 뜻이 아니다.

### 표현해야 할 것

- 부드러운 큰 명암 변화, 형태를 따라 칠한 부피감, 두툼하고 읽기 쉬운 베벨.
- 선택적인 모서리 마모와 적은 수의 큰 디테일. 벽·바닥·프랍이 같은 사람이 칠한 듯한 붓질 크기.
- 중앙 바닥은 조용하게 유지. 프랍은 외곽에서 공간의 성격을 만든다.

### 피할 것

- 표면 전체에 뿌린 거친 노이즈·긁힘, 과도한 붓자국, 실사 PBR 금속 반사.
- 모든 타일을 밝은 코랄 선으로 둘러 그리드만 두드러지는 결과.
- 전체를 어둡게 눌러 바닥/벽/프랍/플레이어가 한 덩어리로 뭉치는 결과.
- 강한 방향 그림자·조명 글로우를 알베도에 구워 두는 것.
- 단색 재질과 조명만으로 핸드페인팅 텍스처 제작을 끝냈다고 보고하는 것.

## 5. 모델링·UV 계약

- 단위 1m. Godot은 +Y 위, -Z 정면, +X 오른쪽. Blender는 Z-up이며 이 프로젝트 파이프라인의 +Y 정면이 Godot -Z로 변환된다.
- 배치 그리드 .25m, 바닥 기본 피치 2m, 벽 높이 3m. 길이를 맞추려고 메시 전체를 비균일 스케일하지 않는다.
- F01 피벗: 좌측 앞 윗모서리. X/Z=0~2, Y=-.2~0. 실제 폭은 줄이지 않고 상단 경계 안쪽 8mm 베벨로 이음을 표현한다.
- W01 피벗: 좌측 앞 바닥. X=0~2, Y=0~3, Z=0~.25. 정면은 -Z. ㄱ자 코너는 중복 벽면과 관통이 없게 끝 구간을 정리한다. 새 장식 파츠로 가리지 않는다.
- A01/A02 피벗: 바닥 중심. X/Z 중앙 정렬, Y=0부터 각각1/2m. 작업대 후면은 벽에서 .05m 띄운다.
- A01은 빈 상판, 좌우 서랍 받침과 중앙 무릎 공간. 상판/서랍을 하위 메시로 구분하되 애니메이션은 만들지 않는다.
- A02는 서로 높이가 다른 앞문 2개, 코랄 손잡이, 낮은 발. 손잡이는 정면에만 있고 평면에서도 같은 면으로 투영되어야 한다.
- 건축 일반 베벨 20~40mm, 바닥 맞닿는 경계8mm, 프랍10~20mm를 출발점으로 사용한다. 게임 카메라 가독성을 보고 조절하되 외형 치수와 접속을 깨지 않는다.
- 닫힌 면·정상 노멀·UV·접지·피벗을 검사한다. 불필요한 내부 면은 줄이고 부피감을 만드는 큰 실루엣은 보존한다. 폴리곤 수만으로 품질을 판정하지 않는다.

텍스처 제작 기준:

- 공통 **512px/m**, 2048px = 4m. F01 2m는 1024px 범위를 차지한다.
- `BASE` 반복 보라 금속, `TRIM` 벽/베벨/코랄 도장, `PROP` 공용 프랍 아틀라스를 사용한다. 이번에 쓰지 않는 배관 등의 아틀라스 영역까지 완성할 필요는 없다.
- BASE는 타일별 UV 위상을 월드 배치에 맞춰 이어 4m 주기를 유지한다. 모든 2m 타일에 동일한 절반 UV만 반복하여 경계가 끊어지지 않게 한다. 90도 회전 사용 시에도 이음과 명암 방향을 따로 검사한다.
- 프랍 공용 아틀라스는2048px, 패딩 기준16px. 실제 mip에서 번짐이 없는지는 엔진에서 확인한다.
- Roughness .75~.9를 출발점으로 하고 틈 AO는 약하게 사용한다. 재질/텍스처를 인스턴스마다 복제하지 않고 공유한다.
- Blender 전용 셰이더가 GLB에 그대로 옮겨진다고 가정하지 않는다. Godot에서 사용할 베이스컬러 텍스처와 재질이 실제로 연결된 결과를 확인한다.

## 6. 적용 방법 — 먼저 작은 시험 공간

다음은 착수 후 실행할 기본안이다. 이번 문서 작성으로 씬이나 파일이 생성된 것은 아니다.

1. **착수 상태 확인:** `git status`와 최신 `AGENTS.md`를 확인한다. 다른 에이전트의 변경/미추적 파일을 보존하고, 겹치는 파일은 역할을 조율한다.
2. **F01/W01 블록아웃:** 16장 바닥과 ㄱ자 벽을 배치하고 현재 플레이어 크기와 카메라에서 확인한다. 단위·피벗·접지부터 고정한다.
3. **바닥/벽 텍스처:** F01→W01 순으로 재질을 완성한다. 바닥3×3 이상 반복과 벽 연속 배치를 먼저 확인한다.
4. **큰 프랍:** A01→A02 순으로 제작해 외곽에 하나씩 배치한다. 중앙 이동/공격 공간을 비우고 작은 소품은 추가하지 않는다.
5. **Godot 시험 적용:** 별도 배경 시험 씬 또는 명시적인 시험 모드에서 실제 GLB/텍스처를 로드한다. 현재 `CameraRig`와 플레이어/전투 표시를 사용해 확인한다. 본편 기본 배경을 전역 교체하지 않는다.
6. **비교·수정:** 같은 카메라·해상도·조명에서 전체 화면과 근접 화면을 저장한다. 원화 대조, 색면/베벨 수정, 이음/충돌 검사 후 결과를 사용자에게 보여준다.

실행 시 먼저 확인할 기존 연결 지점은 `scripts/main.gd`의 `_build_environment()`·`_build_arena()`, `scripts/camera_rig.gd`, `scripts/terrain.gd`, `scripts/presentation/painted_look.gd`다. 이는 확인 후보이지 지금 수정하라는 지시가 아니다. 기존 재질 덮어쓰기나 지형 생성이 새 에셋에 어떤 영향을 주는지 읽은 뒤 최소 범위로 연결한다.

시험 씬 조명은 현재 전투 환경을 기준으로 시작한다. 원화처럼 보이게 하려고 시험 씬만 과도하게 꾸민 뒤 본편에서도 같다고 주장하지 않는다. 조명이 필요하면 시험 씬 안에서 조절하고, 기준 조명 결과도 함께 남긴다.

충돌은 렌더 메시와 분리한 단순 형상을 사용한다. 바닥 상면은 Y=0, 타일마다 겹친 충돌면을 쌓지 않는다. 벽/프랍 경계에서 걸림·대시 관통을 확인한다. 기존 굴곡 지형 전체를 평평한 타일로 대체하거나 캐릭터 충돌/이동 수치를 변경하는 것은 범위 밖이다.

## 7. 예정 산출물

아래 이름은 제안이며 **아직 존재하는 구현 파일이 아니다**. 기존 동일 이름이 있으면 먼저 확인하고 덮어쓰지 않는다.

이 목록은 최초 계획의 일반 이름이다. 실제 착수 시에는 10절의 작업자별 접두사를 우선한다. 별도 작업 결과의 실제 경로/진행 상태는 각 작업 기록을 확인한다.

- 원본: `models/src/bg_floor_f01.py`, `bg_wall_w01.py`, `bg_workbench_a01.py`, `bg_locker_a02.py`.
- 모델: `assets/models/bg_floor_f01.glb` 등4종, 각각의 `.import`.
- 텍스처: `assets/textures/background/first_pass/` 아래 공용 베이스컬러/필요 맵과 `.import`.
- 편집 가능한 `.blend`·개별 모델 미리보기·치수/삼각형/재질 통계: 기존 `output/models/<이름>/` 규칙.
- 시험 적용안: `scenes/background_first_pass.tscn` 및 필요한 전용 스크립트/실행 진입점. 현재 게임 메인 씬을 바꾸지 않고 열 수 있게 한다.
- 최종 비교 캡처·검증 로그·남은 문제: `output/background-first-pass/` (`.gdignore`, 연속 프레임은 git 제외).
- 실제 구현/검사 결과와 실행법을 이 문서 및 `AGENTS.md`에 갱신한다. 생성한 `.uid`/`.import`는 원본과 함께 보존한다.

텍스처 제작 방식은 사용하는 에이전트의 도구와 프로젝트 규칙을 따르되, 편집 가능한 원본/프롬프트 등 재현 근거를 남긴다. 원화 시트 전체를 잘라 그대로 UV에 붙여 라벨·조명·투시가 들어간 것을 최종 텍스처로 삼지 않는다.

## 8. 검증과 완료 기준

착수 후 사용할 명령의 예시다. **문서 작성 단계에서는 실행하지 않는다.**

```powershell
powershell -File tools\blender.ps1 model models\src\bg_floor_f01.py
powershell -File tools\godot.ps1 wait --headless --import
run_tests.cmd
powershell -File tools\godot.ps1 wait --fixed-fps 60 res://scenes/main.tscn -- --bot --seed=1 --seconds=60
```

항상 고정 실행기를 사용한다. Godot 버전은 `godot-version.txt`, Blender 버전은 `blender-version.txt`를 따른다. 시험 씬을 구현하면 그 씬의 `--bot`/자동 캡처도 연결해 따로 검사하고 실제 실행 명령을 기록한다. 기존 main 봇만 통과한 것은 새 배경 검증이 아니다.

완료 체크리스트:

- [ ] 4종 모두 원본·GLB·UV·실제 텍스처·재질이 있고 재빌드할 수 있다.
- [ ] Godot 재임포트 후 크기·축·피벗·접지·노멀이 맞는다.
- [ ] 8×8m 바닥16장에 빈틈/중복 표면/z-fighting이 없고, 벽 코너가 자연스럽게 연결된다.
- [ ] 바닥/벽의 반복 이음, UV 위상, 텍셀 밀도, mip 번짐을 실제 렌더로 확인했다.
- [ ] 작은 장식 없이도 보라 바닥·회보라 벽·코랄 작업대·보라 수납장이 구분된다.
- [ ] 기본 게임 카메라에서 플레이어·적·공격 표시가 배경에 묻히지 않고, 가까이 봐도 핸드페인팅의 큰 면과 베벨이 읽힌다.
- [ ] 실제 이동/대시/사격 등 기존 동작으로 바닥·벽·프랍 충돌과 시야 가림을 확인했다.
- [ ] 변경에 필요한 전체 회귀와 변경 씬 자동 플레이에서 `ERROR`/`SCRIPT ERROR`를 확인하고, 기존 오류와 새 오류를 구분해 보고했다.
- [ ] 전체 화면·반복 이음·프랍 근접 비교 캡처와 통계/로그를 남겼다.
- [ ] 본편 전역 교체/다른 파츠 추가/감염 작업으로 범위를 넓히지 않았다.

기존 키트의 60항목 검사는 도면 파일/설계 수치 검사일 뿐이다. 이를 새 모델의 GLB 적합성·텍스처 이음·엔진 가독성 검증으로 재사용해 완료라고 보고하지 않는다.

- 마지막 중단점/실행 명령/검증 결과/남은 문제는 작업자가 실제 수행한 내용만 갱신한다.

### 충돌 방지용 경로 계약

사용자가 각 작업자에게 제작을 승인한 뒤 적용한다. 같은 4종의 비교안을 따로 만들 경우에도 공유 파일에 서로의 결과를 덮어쓰지 않는다.

| 구분 | Codex 전용 | Claude 전용 |
|---|---|---|
| 모델 원본 / GLB | `bg_codex_*` | `bg_claude_*` |
| Blender 제작 도구 | `tools/blender/codex_background_*` | `tools/blender/claude_background_*` |
| 게임 스크립트 | `scripts/codex_background/` | `scripts/claude_background/` |
| 시험 씬 | `scenes/codex_background_first_pass.tscn` | `scenes/claude_background_first_pass.tscn` |
| 실행 파일 | `codex_background_test.cmd` | `claude_background_test.cmd` |
| 결과 폴더 | `output/codex-background-first-pass/` | `output/claude-background-first-pass/` |
| 작업 기록 | [Codex 기록](background-first-pass-codex.md) | [Claude 기록](background-first-pass-claude.md) |

- 공용 텍스처도 작업자별 경로/파일명으로 분리한다. `.blend`는 `output/models/bg_<작업자>_<이름>/`에 둔다.
- 기존 본편·플레이어·카메라·로비·공용 실행기는 읽기 전용으로 참고한다. 별도 시험 씬에서 상속/어댑터로 연결하고, 공용 파일 변경이 꼭 필요하면 먼저 사용자와 담당을 확인한다.
- `AGENTS.md`에는 자신의 상태 링크만 최소 추가한다. 다른 작업자의 상태 항목·미추적 모델·출력 이미지는 지우거나 수정하지 않는다.
- 이 문서는 공통 규격이다. 한 작업자의 검증 통과를 다른 작업자의 검증 결과로 보고하지 않는다. 어느 안을 본편에 채택할지는 사용자가 결정한다.
